# deltasync

DB를 옮길 때, 옮기는 사이에 쌓인 새 데이터만 골라 안전하게 옮기고, 잘 옮겨졌는지 확인하는 작은 도구입니다.

> 현재는 **SQLite용 데모**입니다. PostgreSQL 등 다른 DB에서는 아직 실행해 보지 않았습니다.

## 한 문단 설명

가게의 낡은 장부를 새 장부로 옮긴다고 생각해 보세요. 어제 저녁에 장부를 통째로 복사해 두었지만, 가게는 오늘도 낡은 장부에 거래를 적었습니다. 이 상태에서 새 장부로 갈아타면 **어제 저녁 이후의 거래가 새 장부에 없습니다.** 이 도구는 갈아타기 직전에 "새 장부에 없는 거래만" 찾아 옮기고, 옮긴 뒤에 "빠지거나 바뀐 거래가 없는지" 확인합니다.

## 용어

| 용어 | 뜻 |
|---|---|
| 원본 / 대상 | 옮겨 오는 쪽 DB / 옮겨 가는 쪽 DB |
| 스냅샷 | 어느 순간의 DB를 통째로 복사해 둔 것 |
| 컷오버 | 사용자가 쓰는 DB를 옛 시스템에서 새 시스템으로 바꾸는 순간 |
| 델타 | 스냅샷 이후에 새로 생긴 차이 |
| PK(기본키) | 행마다 붙은 고유 번호. 같은 번호가 두 번 나오지 않습니다 |
| 기준선 | 작업 직전 원본의 상태를 기록한 파일. 나중에 비교하는 기준입니다 |
| 멱등 | 같은 작업을 여러 번 해도 결과가 같다는 뜻 |
| 롤백 | 문제가 생겼을 때 이전 상태로 되돌리는 것 |
| dry-run | 실제로 바꾸지 않고 결과만 미리 보여 주는 모드 |

## 어떤 문제를 푸나요

| 상황 | 단순하게 하면 | 이 도구는 |
|---|---|---|
| 행 번호가 무작위 문자열(UUID)이거나 두 칸짜리(복합키) | "가장 큰 번호 이후만 옮기기"가 안 됩니다 | 양쪽 번호 목록을 전부 비교해, 대상에 없는 행만 옮깁니다 |
| 두 DB의 칸 구성이 다름 | 옮기다 오류가 납니다 | 양쪽에 모두 있는 칸만 옮기고, 빠지는 칸은 알려 줍니다 |
| 실수로 두 번 실행 | 같은 행이 두 번 들어갑니다 | 이미 있는 행은 건드리지 않아 결과가 같습니다 |
| 옮기다 중간에 실패 | 일부만 옮겨진 상태로 남습니다 | 전부 옮기거나 전부 취소합니다 |
| 잘 옮겨졌는지 | 눈으로 보면 놓칩니다 | 기준선과 행 단위로 비교합니다 |
| 새 DB로 갈아탄 뒤 되돌아갈 때 | 새 DB에만 쌓인 데이터가 사라집니다 | 되돌릴 때 옮겨야 할 행을 미리 계산합니다 |

## 써 보기

설치는 필요 없습니다. Python만 있으면 됩니다. (Python 3.13, Windows에서만 확인했습니다.)

```bash
# 1. 연습용 DB 만들기
python examples/make_demo_data.py demo_data

# 2. 작업 전 상태 기록 (기준선)
python -m deltasync baseline --db demo_data/source.db --out demo_data/baseline.json

# 3. 무엇이 옮겨질지 미리 보기 (아직 아무것도 바꾸지 않음)
python -m deltasync apply --source demo_data/source.db --target demo_data/target.db

# 4. 실제로 옮기기
python -m deltasync apply --source demo_data/source.db --target demo_data/target.db --execute

# 5. 잘 옮겨졌는지 확인
python -m deltasync verify --db demo_data/target.db --baseline demo_data/baseline.json
```

3번의 출력 예시입니다.

```
== 델타 계획 ==
  events: 반영 대상 10행  (원본에만 있는 컬럼(이관 제외): feature)
  [건너뜀] notes: PK가 없어 행 식별 불가
  orders: 반영 대상 5행  (원본에만 있는 컬럼(이관 제외): coupon)
  users: 반영 대상 5행  (대상에만 있는 컬럼(기본값/NULL): plan)
  합계: 20행

[dry-run] 변경하지 않았습니다. 반영하려면 --execute 를 붙이세요.
```

5번이 통과하면 `검증 통과`가 나오고 종료 코드는 `0`입니다.

그 밖의 명령입니다.

| 명령 | 하는 일 |
|---|---|
| `profile --db 파일` | 테이블마다 PK 종류, 행 수, PK가 겹치지 않는지 보여 줍니다 |
| `plan --source A --target B --reverse` | 대상에만 있는 행을 원본으로 되돌릴 때 필요한 목록을 계산합니다 |
| `verify ... --strict` | 기준선에 없던 추가 행도 실패로 처리합니다 |

종료 코드는 `0` 성공, `1` 검증 실패, `2` 사용 오류입니다. **기준선 파일이 없으면 통과가 아니라 실패(2)입니다.** 비교할 기준이 없는데 통과로 처리하면, 검증기가 아무것도 확인하지 않고 "문제없음"을 내기 때문입니다.

## 확인 방식

기준선의 모든 행이 대상에 같은 값으로 있는지 봅니다.

| 발견한 것 | 결과 |
|---|---|
| 행이 빠짐 / 값이 바뀜 / 테이블이 없음 | 실패 |
| 대상에만 있는 추가 행 | 기본은 참고만. `--strict`면 실패 (갈아탄 뒤 정상적으로 쌓였을 수 있어서) |
| 대상에 칸이 없는 컬럼 | 비교에서 빼고 알려 줍니다 |

## 테스트

```bash
python -m unittest discover -s tests -v
```

17개이고, 전부 통과합니다. 그중 6개는 **일부러 대상을 망가뜨려서, 검증기가 정말 실패를 내는지** 확인합니다. "통과하는 경우"만 시험하면 검증기가 항상 통과를 내도 알 수 없기 때문입니다.

| 일부러 낸 문제 | 기대 결과 |
|---|---|
| 행 삭제 | 실패 |
| 값 변경 | 실패 |
| 테이블 삭제 | 실패 |
| 기준선에 없는 추가 행 | 기본은 통과, `--strict`는 실패 |
| 기준선 파일 없음 | 실패 (종료 코드 2) |
| 기준선 파일 손상 | 실패 |

## 하지 않는 것 / 확인하지 못한 것

- **PostgreSQL에서 실행해 보지 않았습니다.** SQLite로만 확인했습니다.
- **없는 행을 추가하는 일만 합니다.** 값이 바뀐 행을 고치거나 지워진 행을 삭제하지 않습니다. 바뀐 행은 `verify`가 찾아서 알려 줄 뿐입니다.
- 행 번호 목록을 메모리에 올립니다. 수만 행 규모의 데모이고, 수천만 행에는 맞지 않습니다.
- PK가 없는 테이블은 행을 구분할 수 없어 옮기지 않고 건너뜁니다.
- 테이블 간 참조 관계(외래키) 순서를 따지지 않습니다. 이름순으로 처리합니다.
- 옮기는 동안 원본에 계속 쓰기가 일어나는 상황은 다루지 않습니다. **쓰기를 먼저 멈춘 뒤** 옮기는 것을 전제로 합니다.
- 기준선의 행 요약값은 변경 감지용이며 보안 목적이 아닙니다.

## 파일 구성

```
deltasync/
  db.py        DB 연결과 테이블 정보 읽기
  delta.py     무엇을 옮길지 계산하고, 한 번에 옮기기
  baseline.py  기준선 저장과 비교
  cli.py       명령어
examples/      연습용 DB 만드는 스크립트
tests/         동작 확인 테스트와 일부러 망가뜨리는 테스트
docs/AI_LOG.md AI가 만든 코드의 오류와 수정 기록
```

## 만든 방식

Claude Code로 구현했습니다. 설계 방향(번호 목록 전체 비교, 공통 칸만 옮기기, 기준선이 없으면 실패, 일부러 망가뜨려 검증기 확인)은 실제 DB 이관 작업에서 겪은 문제를 바탕으로 정했고, 구현은 AI와 함께 진행한 뒤 테스트로 확인했습니다. 작업 중 나온 AI 코드의 오류와 수정은 [docs/AI_LOG.md](docs/AI_LOG.md)에 남깁니다.
